PSP Modding Studio v0.14.5

Platform documentation

PSP Modding Studio is a browser-based workspace for PSP modding. The Studio manages projects, files, tabs, search, tool discovery and data transfers. Individual editors live in independent Tools hosted by the Studio.

The central rule: the Studio owns the workspace; tools own editing. A tool should never need to know how the Project Explorer, tab system, Tool Library or project persistence are implemented.

1. Philosophy

PSP Modding Studio deliberately separates the wrapper from the editors that run inside it. The wrapper is intentionally generic: it knows files, folders, project preferences and tool metadata, but it does not know what an ISO, SFO, PRX, texture, script or game-specific format means.

This makes the platform scalable. A new editor can be added without teaching the Studio its internal file format, UI or workflow. In the codebase these plugin-like components are called Tools.

The Studio owns

  • Projects and .pspstudio persistence.
  • Project Explorer and workspace file operations.
  • Search across project files.
  • Tool discovery and compatibility matching.
  • Open With, pins, suggestions and file associations.
  • Document tabs and tool iframe lifecycle.
  • Safe drag-and-drop routing between project and tools.

Each Tool owns

  • Its own UI and internal state.
  • Parsing and rebuilding its file formats.
  • Tool-specific validation and editing rules.
  • Tool-specific previews, inspectors, properties and shortcuts.
  • Any optional external services or libraries it needs.

What the Studio intentionally does not do

The wrapper does not parse an ISO just because an ISO is present in the project. It does not inspect an SFO to decide which tools should exist. It does not contain a game registry. It does not provide a global inspector for tool-specific properties. It also does not expose an API that lets one tool hard-code and launch another tool by ID.

When a responsibility is format-specific, it belongs to a Tool. When it is workspace-wide and format-agnostic, it belongs to the Studio.

2. Quick start

  1. Create or open a project. Use the New/Open icons in the top bar. A project is required before tools and workspace operations are enabled.
  2. Add files. In Project Explorer use New file, New folder or Import files. You can also drag files from the operating system into the Explorer.
  3. Open a file. Double-click it or press Enter. The Studio chooses a compatible tool or opens the Open With dialog.
  4. Edit inside the tool. Each tool runs in its own tab and controls its own editing UI.
  5. Move results back to the project. If a tool exposes a draggable file/folder resource, drag it into Project Explorer.
  6. Save the project. Use the Save icon or Ctrl+S / ⌘+S. The project is saved as a .pspstudio file.
No server-side workspace exists. The Studio is a static client-side application. Your project is in memory until you save it. Individual tools may have their own network requirements, but the wrapper itself does not upload your project to a backend.

3. Interface

Top bar

The top bar contains only the three global project actions that need to be permanently visible:

New project
Creates a new empty workspace.
Open project
Loads a previously saved .pspstudio file.
Save project
Writes the current workspace back to a .pspstudio file.

The project name appears in the same bar. An asterisk (*) means that the project contains changes that have not yet been saved.

Activity rail

The vertical rail is the Studio's permanent navigation surface:

  • Explorer - shows Project Explorer.
  • Search - searches filenames and file contents across the project.
  • Pinned tools - workspace-specific tool shortcuts appear between Search and the lower utility section.
  • Tool Library - browses the bundled tool catalog and manages pins.
  • Help - opens this documentation in a separate browser tab.

Explorer and Search reuse the same left sidebar. Clicking the active Explorer/Search icon again collapses the sidebar.

Document tabs

Tools and Studio-owned utility pages such as Tool Library open in the central document area. Switching tabs leaves a tool alive. Closing a tool tab destroys that tool instance.

A dot next to a tab title means the tool has declared its own internal state dirty. This is separate from the project dirty state: a tool can contain unsaved internal edits even when the .pspstudio project itself has not changed.

4. Projects and .pspstudio

A project is a generic tree of files and folders plus a small amount of workspace metadata. The project does not contain tool-specific models or parsed objects.

What is saved

  • Every project file and folder.
  • The project name.
  • Pinned tool IDs.
  • Suggested tool IDs.
  • Open With file associations.
  • Restorable tool-tab descriptors.

Search results, temporary drag operations, modal dialogs and tool runtime memory are not persisted.

File format

A .pspstudio file is a ZIP-based container. At a high level it looks like:

project.pspstudio
|--- project.json
`--- workspace/
    |--- EBOOT.BIN
    |--- PARAM.SFO
    `--- assets/
        `--- icon.png

project.json contains project metadata and workspace preferences. User files live under workspace/. The format is intentionally simple enough to inspect for recovery purposes, but manual edits are not recommended because the Studio validates archive structure, paths, sizes and checksums when opening it.

A simplified manifest looks like:

{
  "format": "psp-modding-studio-project",
  "version": 1,
  "name": "My PSP Project",
  "savedAt": "2026-08-14T12:00:00.000Z",
  "workspace": {
    "pinnedTools": ["sfo-studio"],
    "suggestedTools": ["image-studio"],
    "fileAssociations": {
      "name:param.sfo": "sfo-studio"
    }
  },
  "tabs": []
}

This is documented for transparency and recovery, not as a plugin interface. Tool authors should not edit project.json or depend on its internal persistence details.

Saving

When the browser supports the File System Access API, the Studio can reuse a selected file handle and save directly to it. In other browsers it falls back to a normal browser download.

Saving is revision-safe. If the project changes while a large save is being generated, the saved snapshot remains valid but the Studio keeps the project marked dirty so that the later change cannot be mistaken for already-saved data.

Restoring tabs

The Studio stores lightweight descriptors for tool tabs. On reopen it attempts to restore them if the referenced tool and file still exist. Failure to restore a tool does not prevent the project from opening and does not delete project files.

5. Project Explorer

Project Explorer is the canonical view of the workspace tree. File and folder mutations belong here rather than inside a global Edit/Project menu.

Header actions

New file
Creates a new empty binary file in the selected folder. The initial content is zero bytes; the filename determines which tools may later accept it.
New folder
Creates an empty project folder.
Import files
Selects one or more existing files from your computer and copies their contents into the project.

New file and Import are intentionally different. New file creates something that did not exist before; Import copies existing local files into the workspace.

Context menu

Right-click a node for the operations relevant to that node:

  • Open / Open With for files.
  • New File / New Folder / Import Files for folders.
  • Rename, Copy, Paste and Delete where applicable.

Copy/Paste uses an Explorer-owned in-memory clipboard. It does not depend on the operating system clipboard and does not duplicate file Blobs in memory just to perform the copy.

Drag and drop

The entire Explorer surface is a valid drop area:

  • Drop on a folder -> the item goes into that folder.
  • Drop on a file -> the item goes into that file's parent folder.
  • Drop on empty Explorer space -> the item goes into the project root.

Dragging an existing project node moves it. Dragging native files from the operating system imports them. Dragging a semantic resource from a tool copies the tool's exported data into the project.

6. Workspace Search

Search is wrapper-owned because it operates across the project rather than inside one file format. It deliberately stays simple: exact filename/content search, no persistent index and no format-specific parsers.

Filename search

Every query also searches project paths. Filename/path matching is case-insensitive and is available for all files regardless of size.

Text search

Text mode converts the query to UTF-8 and searches for that exact byte sequence. Content matching is exact and therefore case-sensitive.

sceKernelLoadModule

This is intentionally not a regex engine and does not guess encodings other than UTF-8.

Hex search

Hex mode searches exact bytes. Spaces and letter case in the query are ignored:

DE AD BE EF

DEADBEEF

Both forms search the same four bytes. Wildcards such as DE ?? BE ?? are not part of the wrapper search; that belongs in a specialized pattern-scanning tool.

Large files and Deferred results

The Studio never loads every project file into RAM at once just to search it. Content scanning runs in a Web Worker and reads files in chunks.

  • Files up to 32 MiB each are eligible for automatic content scanning.
  • Automatic scanning stops after an aggregate budget of 256 MiB for one search.
  • Remaining files appear under Deferred.
  • You can scan one deferred file or choose Scan all.

Deferred does not mean unsupported; it means the Studio is waiting for explicit permission before spending more time reading large data.

Results and offsets

Content results show byte offsets such as 0x00032A10. Clicking a result opens the file normally. The wrapper intentionally does not expose a cross-tool gotoOffset() API, so the result does not force a particular editor to navigate internally.

Search result counts are bounded to keep the UI responsive: filename results are capped at 1,000 and content results at 2,000 overall (with bounded per-file results). Refine the query when a cap is reached.

Search does not recursively parse formats. If game.iso is one file in the project, wrapper Search sees one binary Blob. Searching the ISO filesystem belongs to an ISO-aware tool.

7. Tool Library

Tool Library lists tools that are already bundled with the deployed Studio. It is a catalog and workspace-customization surface, not a package manager: Pin/Unpin does not download or install code.

Core tools

A Core badge means the tool is part of the baseline catalog and always available to the Studio. Core status is independent from pinning: a core tool can still be pinned to the activity rail for convenience.

Pinning

Pinning is workspace-specific. New projects start with UMD Forge pinned because it is the primary disc-workspace tool; you can unpin it at any time. Any pinned tool receives a persistent icon in that project's activity rail. Unpinning removes the shortcut but does not make the tool unavailable from Tool Library or Open With.

Pins are saved inside .pspstudio, so different projects can expose different tool shortcuts.

8. Opening files and Open With

Each tool declares which filenames it can accept. When you open a project file, the Studio asks the Tool Registry for compatible handlers.

Automatic opening

  • If a saved compatible association exists, the Studio uses it.
  • Common browser-supported images open in Image Viewer by default. Use Open With when you want Image Studio or another compatible editor.
  • If exactly one format-specific tool is compatible, it opens directly.
  • If no format-specific tool exists, Hex Viewer is the generic fallback.
  • If several format-specific tools compete and no default is saved, the Open With chooser appears.

Open With ranking

Compatible tools are grouped in this order:

  1. Pinned - tools explicitly pinned to this project.
  2. Suggested - tools previously chosen successfully through Open With in this project.
  3. Core - other compatible baseline tools.
  4. Other compatible tools.

A suggestion is not a pin and does not create a rail icon. Suggestions are simply workspace-local ranking hints.

Always use

Open With can remember a default association. Depending on the file, the association may target an extension such as .bin or an exact filename such as EBOOT.BIN. Associations are stored in the current project.

The choice is committed only after the selected tool successfully opens the file. A broken tool cannot leave behind a successful-looking suggestion or association.

Force the chooser

Use Open With... from the context menu or press Shift+Enter on a selected file even if a default handler already exists.

9. Moving data between project and tools

The Studio does not require tools to import ProjectStore APIs. Transfers use normal drag-and-drop plus a very small semantic contract.

Project -> Tool

A project file can be dragged onto a tool element that accepts a file or folder drop. The wrapper converts the file into the target iframe's JavaScript realm before handing it to the tool.

Tool -> Project

A tool can expose a semantic file or folder resource. The wrapper makes it draggable automatically. Drop it anywhere in Project Explorer and the Studio materializes it into the workspace.

Tool -> Tool

Tool-to-tool drag is supported for file resources when the destination implements the corresponding drop method. Folder transfers between tools intentionally go through Project Explorer so that tree reconstruction has a single owner.

No programmatic cross-tool launcher

Tool API v1 intentionally has no method such as studio.openWith('some-tool'). A tool should not know the IDs or routing rules of other tools. Users can route data through Project Explorer, Open With or direct file drag. A new cross-tool capability should only be standardized if multiple real tools prove that the same interaction cannot be expressed cleanly through the existing model.

11. Troubleshooting

A file does not open

The most common cause is that no catalog tool declares support for its filename. Use Open With to verify available handlers. If the Tool Registry itself failed, the Studio reports it with a toast while project features remain available.

A tool is available but does not appear in the activity rail

The rail only shows tools explicitly pinned for the current project. Open Tool Library and choose Pin. Saving the project persists that pin.

Search leaves a file under Deferred

This is expected for large files or after the automatic scan budget is exhausted. Click Scan on that file or Scan all.

Search results disappear after editing project files

Search results are tied to a project revision. When file contents or tree structure changes, previous content results become stale and the Studio asks you to run the search again.

The project still shows an asterisk after Save

If the project changed while the save snapshot was being generated, the file on disk is valid but does not include that later change. Save again to capture the newest revision.

Closing the project or browser asks for confirmation

The project has unsaved workspace changes, a tool has declared unsaved internal state, or both. Project changes and tool dirty state are tracked independently.

The application does not work when opening index.html directly from disk

PSP Modding Studio uses ES modules, fetch, workers and same-origin iframe hosting. Serve the directory over HTTP/HTTPS instead of using file://. For local development, for example:

python3 -m http.server 8080

Then open http://localhost:8080/.

12. Safety limits and architectural boundaries

The wrapper uses explicit limits so malformed projects or tools fail instead of consuming unbounded memory/time. These are safety boundaries, not recommended project targets.

AreaCurrent bound
Project entries50,000 files/folders
Project nesting128 levels
Single project file512 MiB
Total inflated project archive1 GiB safety envelope
Saved tool tabs256
Pinned tools256
Suggested tools32
File associations1,024
Catalog tools256
Tool iframe load15 s
Tool API call60 s

Trusted tool model

Tools are hosted in same-origin iframes. This gives each tab separate DOM, CSS, JavaScript globals and lifecycle, but it is not a security sandbox against intentionally malicious code. Bundled tools are trusted application code.

An ecosystem for untrusted remote plugins would need a different architecture: sandboxed/cross-origin iframes and a message-based capability protocol. Tool API v1 is intentionally not designed for that use case.

Developer documentation

Creating Tools (plugins)

A Tool is the PSP Modding Studio equivalent of a plugin. It is intentionally just a normal web page plus a small metadata file. You do not inherit a framework class, mount into the Studio DOM or import ProjectStore internals.

13. Tool anatomy

The minimum tool is:

tools/my-tool/
|--- tool.json
`--- index.html

Everything else is optional:

tools/my-tool/
|--- tool.json
|--- index.html
|--- tool.js
|--- style.css
|--- icon.svg
|--- workers/
`--- vendor/

The directory name is the tool ID. Prefer lowercase IDs such as sfo-studio, texture-editor or game-script-tool. A tool ID may contain letters, digits, dots, underscores and hyphens, must not contain path separators, and is limited by the Registry.

Tools are standalone pages

index.html should remain usable as a normal page while developing the tool. When hosted by PSP Modding Studio it is loaded in its own same-origin iframe. The Studio sets these attributes on the tool document:

document.documentElement.dataset.theme === "dark"
document.documentElement.dataset.studioHosted === "true"

A tool may use them for minor presentation adjustments, but should not depend on wrapper CSS classes or DOM structure.

Static paths and subdirectory hosting

Write tool asset URLs so the tool works when PSP Modding Studio is deployed below a site subdirectory (for example GitHub Pages). Prefer paths relative to the file that owns the reference:

<link rel="stylesheet" href="./style.css">
<script type="module" src="./tool.js"></script>
<img src="./assets/preview.svg" alt="">

Inside CSS, remember that url(...) is resolved relative to the stylesheet, not the HTML document. Avoid root-absolute paths such as /assets/... unless the deployment explicitly guarantees a domain root. A tool's own icon path in tool.json is resolved relative to the tool folder.

Project file icons are not tool metadata

The icon shown beside a project file in Explorer is chosen by the Studio from the filename/extension. A tool should not register project-file icon mappings. The icon field in tool.json represents the tool itself in Tool Library, tabs and the activity rail.

14. tool.json

The manifest lets the Registry discover and validate a tool without executing tool code.

{
  "api": 1,
  "name": "My Tool",
  "subtitle": "Optional short subtitle",
  "description": "What the tool does.",
  "author": "Your Name",
  "version": "1.0.0",
  "icon": "icon.svg",
  "accepts": [".bin", "EBOOT.BIN"],
  "keywords": ["binary", "psp", "editor"]
}
FieldRequiredMeaning
apiYesTool API version. Current value must be 1.
nameYesHuman-readable tool name.
subtitleNoShort secondary label.
descriptionYesDescription shown in Tool Library/Open With.
authorYesAuthor or maintainer display name.
versionYesTool version; independent from Studio version.
iconNoRelative path to the tool icon. A default icon is used when omitted.
acceptsNoFilename rules used by Open With.
keywordsNoAdditional Tool Library search terms.

accepts rules

Compatibility rules are case-insensitive and may be:

  • .sfo - any filename ending in that extension.
  • EBOOT.BIN - exact filename.
  • * - every filename.

Do not put MIME types, paths or regular expressions in accepts. If a tool can only make a final decision after parsing the file, declare the narrowest useful filename rule and validate the content inside open(file).

Icon rules

icon must be relative to the tool folder. Absolute URLs, .. escapes and paths that leave the tool directory are rejected. Example:

"icon": "assets/icon.svg"

15. Registering a tool

Adding files under tools/ is not enough. Register the directory name in tools/catalog.json:

{
  "core": [
    "umd-forge",
    "sfo-studio"
  ],
  "tools": [
    "my-tool"
  ]
}

Core vs regular catalog tools

  • core - baseline tool shipped as a permanent part of the Studio distribution.
  • tools - normal bundled catalog entry.

Core status is a catalog concern, not a manifest field. A Tool must never declare itself pinned, suggested, associated or core inside tool.json. Those are Studio/workspace decisions.

The Registry loads manifests independently. If one tool is malformed or its page is missing, that tool is isolated while valid sibling tools remain available.

16. Tool API v1

A hosted tool may expose a global window.tool object containing any relevant subset of four methods:

window.tool = {
  open(file) {},
  get(id) {},
  replace(id, file) {},
  add(id, files) {}
};

The API is intentionally tiny. Do not import Studio classes to compensate for missing convenience methods.

open(file)

Called when the Studio opens a project file with the tool. The argument is a real File created in the tool iframe's JavaScript realm.

window.tool = {
  async open(file) {
    const bytes = new Uint8Array(await file.arrayBuffer());
    loadDocument(bytes, file.name);
  }
};

If a file is opened through Open With, the selected tool must implement open(file). A tool that does not accept project files may omit it.

get(id)

Called when a semantic data-file or data-folder resource is dragged out of the tool. The id is the exact opaque string declared by the tool in HTML.

For a file, return a File when possible; a real Blob is also accepted:

get(id) {
  if (id !== 'output.bin') return;
  return new File([buildBytes()], 'output.bin', {
    type: 'application/octet-stream'
  });
}

replace(id, file)

If this method exists, every valid data-file element becomes a drop target. Exactly one incoming file is accepted.

async replace(id, file) {
  if (id !== 'preview.png') return;
  await loadReplacement(file);
}

add(id, files)

If this method exists, every valid data-folder element becomes a multi-file drop target.

async add(id, files) {
  if (id !== 'assets') return;
  for (const file of files) await importAsset(file);
}

Call behavior

Tool API calls may be synchronous or return Promises. The wrapper places a time bound around hosted calls. Current Tool API calls have a 60-second wrapper timeout, so long operations should be structured so they do not depend on an indefinitely pending single call.

Throw normal Error objects with useful messages when an operation cannot continue. The wrapper catches and attributes tool errors to the tool/method instead of leaving partial wrapper state behind.

17. Semantic file and folder resources

Tools do not register drag handlers with the Studio. They mark ordinary HTML elements with one semantic attribute:

<div data-file="output.bin">Drag output.bin</div>
<div data-folder="export">Drag export folder</div>

A semantic element must declare exactly one of data-file or data-folder. Values are opaque IDs owned by the tool.

File export

<button data-file="patched-eboot.bin">
  Drag patched EBOOT
</button>

<script>
window.tool = {
  get(id) {
    if (id === 'patched-eboot.bin') {
      return new File([patchedBytes], 'EBOOT.BIN');
    }
  }
};
</script>

When get exists, the wrapper makes the semantic element draggable automatically.

Folder export

A folder resource returns an object exposing files. Every entry contains a POSIX-relative path and a File/Blob:

get(id) {
  if (id !== 'export') return;
  return {
    files: [
      { path: 'manifest.txt', file: manifestFile },
      { path: 'assets/icon.png', file: iconFile },
      { path: 'assets/menu/background.png', file: backgroundFile }
    ]
  };
}

Paths must be relative and use forward slashes. These are invalid:

/absolute/file.bin
../escape.bin
folder\windows-path.bin

Lazy folder generation

For large exports, files may be a function that returns an iterable or async iterable:

get(id) {
  if (id !== 'export') return;
  return {
    files: async function* () {
      for (const asset of model.assets) {
        yield {
          path: `assets/${asset.name}`,
          file: await buildAsset(asset)
        };
      }
    }
  };
}

The transfer remains owned by the source and destination lifecycles until the consumer has finished materializing the resource. Closing either side cancels the transfer.

Folder transfers are bounded by the wrapper (including path/depth/node/file limits and a total transfer deadline). Treat these limits as failure containment, not as a target batch size; very large transformations are usually easier to debug when exported in deliberate groups.

Dynamic semantic elements

The host observes the tool DOM. You may add, remove or change data-file/data-folder elements after load; the wrapper updates drag eligibility automatically.

18. Optional window.studio presentation bridge

After the iframe finishes loading, the wrapper injects a reserved read-only window.studio object:

studio.toast('Export complete', 'success');
await studio.confirm('Discard changes?');
studio.dirty(true);
studio.title('EBOOT.BIN - My Tool');
MethodPurpose
toast(message, type, duration)Shows a Studio notification. Types: info, success, warning, error.
confirm(message)Asks for confirmation and resolves to a boolean.
dirty(value)Marks/unmarks the tool tab as internally dirty.
title(value)Updates the tool tab title.

Bridge readiness

A standalone tool page does not have window.studio. Even when hosted, very early top-level script may run before the bridge is injected. Use optional access or listen for studio-ready:

function studioReady(callback) {
  if (window.studio) callback(window.studio);
  else window.addEventListener('studio-ready', () => callback(window.studio), { once: true });
}

window.studio is reserved. A tool must not predefine, replace or mutate it.

The bridge is presentation-only. It deliberately does not expose ProjectStore, tabs, Registry, Open With or other tools.

19. Lifecycle, isolation and error handling

One iframe per tab

Every tool tab gets a separate same-origin iframe. Two tabs of the same tool therefore have independent DOM, globals and in-memory state without a custom instance-management API.

  • Switch tab -> iframe remains alive.
  • Close tab -> iframe is destroyed and its wrapper-owned transfers are cancelled.
  • Change project -> old tool hosts and outstanding transfers are torn down.

Keep standalone compatibility

A strong tool can run at tools/my-tool/index.html without the Studio. Treat window.studio as optional and keep all actual editor logic inside the tool.

Do not depend on shell internals

Never import files such as:

js/core/project-store.js
js/core/module-host.js
js/core/transfer-registry.js
js/core/tab-manager.js
js/core/shortcut-manager.js

Those are implementation details, not plugin APIs. A tool that imports them is coupled to the wrapper and can break during harmless internal refactors.

Do not talk directly to other tools

Do not hard-code another tool's directory/ID or access another tool iframe. Tool API v1 has no programmatic cross-tool open function by design. Exchange user-visible files through semantic resources, Project Explorer and Open With.

Errors should be local and descriptive

If the input file is invalid, reject it in the tool:

async open(file) {
  const header = new Uint8Array(await file.slice(0, 4).arrayBuffer());
  if (!isExpectedHeader(header)) {
    throw new Error(`${file.name} is not a supported MyFormat file.`);
  }
  // Continue only after validation.
}

The wrapper contains the failed tab opening and reports the tool/method that failed. Do not catch an unrecoverable error merely to leave a half-initialized editor visible.

Dirty state

Use studio.dirty(true) when the tool contains changes the user could lose by closing the tab. Set it back to false once those changes have been committed/exported according to the tool's own workflow.

Do not use tab dirty state as a substitute for writing changed files into ProjectStore. The tool and project have deliberately separate dirty states.

Performance

  • Do not parse large files repeatedly on every UI render.
  • Use workers for expensive CPU-bound transformations where practical.
  • Use lazy folder iterators when exporting many generated files.
  • Avoid huge base64 strings; use Blob/File/ArrayBuffer-oriented APIs.
  • Keep Tool API methods bounded and cancellable internally where possible.

Security model

Bundled tools are trusted same-origin application code. Do not add unreviewed hostile third-party code and assume the iframe protects the parent. It does not. The iframe is an operational UI/lifecycle boundary, not a hostile-code security boundary.

20. Complete minimal editable-file Tool

This example opens text files, lets the user edit them, marks the tab dirty and exposes the current file as a draggable resource.

Directory

tools/simple-text/

|--- index.html
|--- tool.js
|--- style.css
`--- icon.svg

tool.json

{
  "api": 1,
  "name": "Simple Text",
  "description": "Minimal text editor example for PSP Modding Studio.",
  "author": "Example Author",
  "version": "1.0.0",
  "icon": "icon.svg",
  "accepts": [".txt", ".ini", ".cfg"],
  "keywords": ["text", "editor"]
}

index.html

<!doctype html>
<html>
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Simple Text</title>
  <link rel="stylesheet" href="./style.css">
</head>
<body>
  <header>
    <strong id="name">No file</strong>
    <div id="export" data-file="document.txt">Drag to Project Explorer</div>
  </header>
  <textarea id="editor" spellcheck="false"></textarea>
  <script type="module" src="./tool.js"></script>
</body>
</html>

tool.js

const editor = document.querySelector('#editor');
const nameLabel = document.querySelector('#name');
const exportTile = document.querySelector('#export');

let fileName = 'document.txt';

function updateStudioDirty(value) {
  window.studio?.dirty(value);
}

function updateTitle() {
  nameLabel.textContent = fileName;
  window.studio?.title(`${fileName} - Simple Text`);
}

async function loadFile(file) {
  fileName = file.name || 'document.txt';
  editor.value = await file.text();
  // The resource ID is opaque. Using the filename makes the drag label useful.
  exportTile.dataset.file = fileName;
  updateTitle();
  updateStudioDirty(false);
}

21. Tool release checklist

Before adding a tool to the shared catalog, verify the following:

  • tool.json is valid JSON and uses "api": 1.
  • The tool folder ID matches the entry in tools/catalog.json.
  • index.html loads without redirects or missing local assets.
  • The tool also loads standalone without assuming window.studio exists.
  • accepts is narrow enough to avoid claiming unrelated files.
  • open(file) validates file content before committing editor state.
  • Every exposed window.tool member is actually a function.
  • data-file/data-folder elements declare exactly one resource type.
  • get(id) returns real File/Blob values, not file-like plain objects.
  • Folder export paths are relative POSIX paths without ...
  • replace and add update only the resource identified by the supplied ID.
  • Tool dirty state is reported with studio.dirty() when data can be lost.
  • Opening two instances of the same tool does not share accidental global state.
  • Closing a tab during pending asynchronous work does not leave required global side effects behind.
  • Large operations do not block the main thread unnecessarily.
  • The tool does not import wrapper internals or hard-code another tool's ID.
  • The icon is local to the tool folder and all static paths work when hosted from a subdirectory.
